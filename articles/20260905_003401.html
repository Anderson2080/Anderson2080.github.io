一、算力账本：伪命题与物理极限

华尔街喜欢“Test-Time Compute”的故事，因为它暗示着算力需求可以无限延伸。但让我们把账算到硅片上。以Llama-3-70B为例，在FP8精度下，模型权重占用70GB。一个100K上下文的请求，其KV Cache在GQA（Grouped Query Attention）下，假设32层、8个KV头、128维，每Token需存储32×8×128×2字节（FP16）= 64KB。100K Token即6.4GB。这意味着一块80GB的HBM3e，在加载权重后仅剩约3.6GB可用作KV Cache，即只能容纳约56K Token的上下文——这还是在无任何系统开销的理想状态下。

现在推演并发场景。假设单机8卡H100，每卡HBM3e带宽为3.35TB/s。一个100K上下文的请求，在Prefill阶段，每Token的Attention计算需读取全部KV Cache（6.4GB）。若批处理大小（Batch Size）为16，则单次迭代需读取102.4GB的KV数据。在FP8下，这对应约102.4GB / 3.35TB/s = 30.5毫秒的纯内存延迟。而计算部分，16个请求的Attention矩阵乘法在H100的989 TFLOPS（FP8稀疏）下，仅需约0.7毫秒。内存与计算比高达43:1。这意味着GPU的计算单元在绝大多数时间内处于饥饿状态，MFU（Model FLOPs Utilization）不会超过2.3%。

更致命的是KV Cache碎片化。当多请求并发时，显存分配器必须处理不同长度的上下文。在80GB HBM3e上，若权重占用70GB，剩余10GB空间将被数百个请求的KV Cache动态瓜分。每个请求的KV Cache在显存中是不连续的物理页，导致TLB（Translation Lookaside Buffer）未命中率飙升。在A100的40MB L2 Cache面前，这种碎片化使得每次Attention计算都退化为随机内存访问，延迟从预期的200ns飙升至1.5μs以上。NVLink的900GB/s带宽在此刻成为最大的拥塞节点——因为跨节点的KV Cache交换必须通过它，而它的延迟是片上SRAM的100倍。

二、架构解剖：为什么现有方案是纸上谈兵

业界提出“CXL内存扩展”和“近存计算”来缓解HBM墙。但CXL 3.0的带宽上限为每通道约128GB/s（PCIe Gen5 x16），延迟高达200ns——这比HBM3e的带宽低两个数量级，延迟高一个数量级。将KV Cache放在CXL内存上，意味着Attention计算必须等待200ns+的远程内存访问，而HBM的本地访问仅需80ns。在100K上下文的场景下，这种延迟差异直接转化为每秒数百万次的额外等待周期，最终使端到端推理延迟增加3-5倍。

硅光互联被吹嘘为“超越铜缆的终极方案”。但让我们审视物理参数：当前最先进的硅光调制器（如Intel的200Gbps/lane PIC）在O波段（1310nm）下，其马赫-曾德尔调制器的半波电压（Vπ）约为1.5V，插入损耗约3dB。这意味着驱动电路需消耗约0.5pJ/bit的能量，加上接收端的跨阻放大器（TIA）与CDR功耗，总链路能效约为1.2pJ/bit。对比NVLink 4.0的铜缆方案，其能效为0.9pJ/bit。硅光并未在能效上胜出，反而因电-光-电转换引入了额外的2dB损耗与更高的误码率（BER需从1e-15放宽至1e-12才能获得足够的光预算）。

更核心的问题在于SRAM面积。一个H100的die面积为814mm²，其中SRAM缓存（L2+寄存器文件）约占40mm²，即5%。在Test-Time Compute中，模型需要频繁存储中间激活值（activation）。若激活值需在片上暂存，以FP8精度计算，一个包含4096个隐藏单元的Transformer层，其激活值大小为4096×4096×2字节=32MB。这远超H100的50MB L2 Cache。结果是，激活值必须被写回HBM，每次写入消耗3.35TB/s带宽中的一部分。当Test-Time Compute需要多次迭代（如Self-Consistency采样32次），每次迭代的激活值写回将消耗额外的带宽，使原本已紧张的内存带宽进一步恶化。

三、互联拓扑：多智能体并发的拥塞数学

当市场谈论“多智能体协作”时，他们忽略了互联拓扑的数学。假设一个推理集群由32个H100节点组成，通过NVLink全互联（NVSwitch）。每个节点的NVLink带宽为900GB/s。若一个智能体需要与另外31个智能体交换KV Cache数据（例如在分布式Attention中），每个节点需发送其KV Cache的1/31。以100K上下文、6.4GB KV Cache为例，每个节点需发送约206MB。在900GB/s的带宽下，这需要0.23毫秒。但若31个节点同时向一个节点发送数据，该节点的接收带宽将成为瓶颈——900GB/s的接收能力面对31×206MB=6.4GB的数据，需7.1毫秒。这比HBM的本地读取延迟高出三个数量级。

硅光互联的拥塞模型更糟。当前Co-Packaged Optics（CPO）方案，如Broadcom的Tomahawk 5，提供51.2Tbps的交换容量，但每个光口的功耗约为5pJ/bit（含SerDes）。对比NVLink的0.9pJ/bit，光互联在能效上倒退5倍。在100K上下文的场景下，若使用CPO进行跨节点KV交换，每交换1GB数据需消耗5焦耳能量。而HBM3e的读写能耗仅为0.4pJ/bit，即每GB消耗0.4焦耳。光互联的能耗是本地内存的12.5倍。这种能量账本决定了：任何依赖光互联进行频繁小数据包交换的架构，在Test-Time Compute中都会因热设计功耗（TDP）限制而被迫降频。

四、成本清算：每Token的真实边际成本

最后，让我们为对冲基金计算真实的单位经济性。一个H100节点的TCO（含折旧、电力、冷却）约为每小时15美元。在100K上下文、批处理大小为16的推理任务中，我们已计算出MFU为2.3%。这意味着有效计算吞吐仅为989 TFLOPS × 2.3% = 22.7 TFLOPS。每Token的计算成本为：22.7 TFLOPS / (100K Token × 16请求) = 14.2 GFLOPS/Token。以H100的FP8峰值能效（约0.5 pJ/FLOP）计算，每Token消耗7.1焦耳。加上内存访问能耗（每Token需读取64KB KV Cache，能耗为64KB × 0.4pJ/bit × 8 = 0.2焦耳），总能耗约7.3焦耳/Token。按0.1美元/kWh的工业电价，每Token的电力成本为7.3焦耳 / 3.6e6焦耳 × 0.1美元 = 2e-7美元。但加上硬件折旧（每小时15美元 / 3600秒 / 每秒生成的Token数），若每秒生成1000 Token，则每Token的硬件成本为15美元 / 3600 / 1000 = 4.2e-6美元。总边际成本约4.4e-6美元/Token。

对比GPT-4的API定价（每百万Token输出60美元），即6e-5美元/Token。表面利润率高达92%。但若考虑Test-Time Compute的多次采样（如32次），成本将乘以32，达到1.4e-4美元/Token——超过API定价的2.3倍。这就是为什么OpenAI限制深度推理的调用次数：物理账本决定了任何“无限推理”的商业模式都是负毛利。除非硅光互联的能效突破至0.1pJ/bit以下，且HBM4的带宽提升至16TB/s，否则Test-Time Compute的规模化应用将始终受制于内存墙与互联功耗的双重绞杀。市场对“推理算力需求”的线性外推，忽略了这些非线性物理约束的指数级恶化。清算时刻，就在这些数字被华尔街真正读懂的那一天。
